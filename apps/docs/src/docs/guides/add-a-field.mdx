The first change most people make is a new field. This page walks one through every file it touches,
in order, and shows what gen says when a step is missing. The example adds an optional customer note
to an order in the commerce service's `orders` module. Paths below start at
`services/commerce/src/modules/`.

## 1. The model is the one source

The field's type is its column: `string | null` with `@Str({ max: 280 })` is a nullable
`varchar(280)`, and the initializer is the default. Nothing else declares the column.

```ts
// orders/models/order.model.ts
/** A note the customer leaves at checkout; shown to staff, never to other customers. */
@Str({ max: 280 })
note: string | null = null;
```

## 2. Generate the migration

```bash
pnpm --filter @acme/service-commerce exec stackra db diff add-order-note
```

`stackra db diff` compares the models with the committed migrations and writes the next step of the
module's own stream, numbered after the last one. Review it, then commit it; once merged to `main` a
migration is frozen, and you never write a `down()`: gen derives the inverse for local, preview and
test databases.

```ts
// orders/database/migrations/0004-add-order-note.migration.ts
/**
 * Stackra file contract:
 * Purpose: adds the nullable `note` column to `orders.orders`.
 * Boundary: a snapshot: literal names only, no import of the model; additive, so it runs in one
 *           transactional step and gen derives its inverse (drop the column).
 * Runtime: node
 * Governing contract: ADR 0159 (as amended by programming model v3.1, AGENTS.md)
 */
import { type Blueprint, Migration, type SchemaBuilder } from "@stackra/database";

/** Existing rows stay valid: the column is nullable. */
export class AddOrderNoteMigration extends Migration {
  /** Adds the column. */
  up(schema: SchemaBuilder): void {
    schema.table("orders", (t: Blueprint) => t.string("note", 280).nullable());
  }
}
```

The table name is relative to the module's Postgres schema, so `"orders"` is `orders.orders`. The
names are literals on purpose: a migration records the schema as it was, and `stackra db check`
replays the whole history on a scratch database and fails if the result differs from the models.

## 3. The wire shapes

Input and output are shape classes whose field types are their rules, the class-validator style
without class-validator: gen compiles each class to one Zod schema. Every shape is its own file in
`schemas/`, also when only one file uses it:

```ts
// orders/schemas/create-order-input.schema.ts, inside CreateOrderInput
/** A note for the staff who pack the order. */
@Str({ max: 280 })
note?: string;

// orders/schemas/order-view.schema.ts, inside OrderView
/** The customer's note, or null when they left none. */
note!: string | null;
```

The service maps the model to the view, so `OrderService#toView` in
`orders/services/order.service.ts` copies `note: order.note`, and the workflow's `createOrder` step
stores `run.input.note ?? null`. App forms derive from the action input, so the console's
quick-order form and the mobile create-order sheet see the field after the next `pnpm gen`, without
a second declaration.

## 4. The label

```json
// services/commerce/assets/lang/en/orders.json and ar/orders.json, under "order"
"note": "Customer note"
"note": "ملاحظة العميل"
```

Code references it as `I18n.orders.order.note`; a key present in one locale only fails gen.

## 5. The console column

The column names a path of the list row, `OrderView`, so a typo is a type error; the resource is
`Resource<Order, OrderView>` because the row differs from the model. Its label is derived from the
key.

```ts
// orders/resources/order/order.resource.ts, inside OrderResource (filters and sort unchanged)
override table(t: Table<OrderView>) {
  return t.columns((c) => [
    c.from("orderId").copyable(),
    c.from("status"),
    c.money("totals.totalMinor", { currency: "totals.currency" }).sortable(),
    c.from("createdAt").sortable(),
    c.from("note").toggleable(),
  ]);
}
```

## 6. The test

```ts
// orders/actions/__tests__/create-order.action.test.ts, inside describe(CreateOrderAction)
/** The note travels from the input to the stored order and back in the view. */
it("stores the customer note", async () => {
  const { input } = await setup();
  const as = actors.customer();

  const placed = await run(
    CreateOrderAction,
    { ...input, note: "Gift wrap" },
    { as, idempotencyKey: "k3" },
  );

  const view = await run(GetOrderQuery, { orderId: placed.output.orderId }, { as });
  expect(view.output.note).toBe("Gift wrap");
});
```

The contract test (`expectBackwardCompatible` in `src/__tests__/stackra-manifest.contract.test.ts`)
passes on its own: an optional input field and a new output field are additive. Making the field
required would be a breaking change and needs a dated change file beside the view,
`orders/schemas/order-view-<yyyy-mm>.change.ts`.

## What gen flags when a step is missing

| You skipped                           | `pnpm gen` / `stackra validate` reports                                    |
| ------------------------------------- | -------------------------------------------------------------------------- |
| the migration                         | `orders.Order.note` has no migration; run `stackra db diff`                |
| `@Str` and its length                 | nothing: the column is `text`; add `@Str({ max })` for a bounded `varchar` |
| a locale of the label                 | `orders::order.note` is missing in `ar`                                    |
| the view field, but a client reads it | the app's `QueryOutput<typeof GetOrderQuery>` has no `note` (type error)   |
| `pnpm gen` after the schema change    | `stackra gen --check` fails: `stackra.manifest.json` is stale              |
